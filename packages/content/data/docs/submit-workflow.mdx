# Submit Workflow

The `/submit` form loads active category options from D1 and sends validated fields to
a server route that writes normalized private submission rows to D1. After that write,
the page visibly confirms that the submission is saved and provides a private resume
link. The submitter can close the badge instructions and finish verification later;
the same browser also remembers the unfinished verification automatically.

The submitter installs the supplied badge and asks the server to verify the live
website. The verifier names and loads the exact submitted URL. The UI distinguishes a
page that loaded without the badge from an unreachable site, timeout, HTTP error,
redirect problem, or malformed response and gives a specific next step. Temporary
fetch failures do not consume the limited badge-content attempts. Only a successful
dofollow badge check enters the maintainer review queue.
A scheduled workflow assigns the maintainer one private GitHub review issue within a
few minutes and records that notification in D1. That issue includes a private,
uncached draft link so the maintainer can see the staged submission in the real
listing-detail layout before deciding. The link works only while the D1 row is
awaiting review and stops working after approval or rejection. The protected
production review workflow can then approve and promote that normalized submission
into the public D1 catalog, or decline it without publishing. The issue is an inbox
entry; D1 remains the submission source of truth.

The application form lives in
`packages/web-core/src/forms/d1-submission-form.tsx`. The server-only write boundary
lives in `apps/serp.software/lib/submissions/repository.ts`.
